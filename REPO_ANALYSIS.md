# Анализ репозитория `nomer2`

## 1) Что это за проект
Проект — CLI-утилита и набор воркеров для мониторинга Telegram-чатов через Pyrogram, фильтрации сообщений по ключевым словам и отправки лидов в сервисный чат бота. Точка входа запускает callback-loop Telegram-бота в отдельном потоке и поднимает CLI-команды Typer.  
Ключевая цепочка обработки: аккаунты → назначения чатов/групп → polling истории чатов → фильтрация/дедуп/TTL → отправка лида + кнопки управления ЧС. 

## 2) Архитектура (по модулям)
- `src/ui/cli.py` — основной интерфейс управления: аккаунты, группы, назначения, join-операции, тестовая отправка.  
- `src/parsing/worker.py` — главный воркер парсинга: читает сообщения, применяет фильтры и пишет дедуп-состояние в SQLAlchemy-модели.  
- `src/leads/*` — форматирование лида, отправка в Telegram Bot API, дедуп-хранилище (SQLite) для части сценариев.  
- `src/groups/*` и `src/assignments/repo.py` — JSON-конфигурация сегментов (groups) и привязки аккаунт↔чаты (assignments).  
- `src/join/*` — очередь join-задач и worker для входа аккаунтов в каналы/чаты.  
- `src/db/*` — SQLAlchemy-модели и подключение к БД (`processed_messages`, `user_chat_hits`, `blacklist`).

## 3) Сильные стороны
1. **Разделение ответственности по пакетам**: UI, parsing, leads, groups, join, db разведены логично.  
2. **Защита от дубликатов на уровне БД**: `UniqueConstraint` по `(chat_id, message_id)` и `(chat_id, user_id)` уменьшает шум лидов.  
3. **Операционный CLI**: покрывает жизненный цикл (добавление аккаунтов, распределение чатов, запуск парсинга, join).  
4. **Базовая отказоустойчивость**: в polling-циклах есть обработка исключений и продолжение работы.

## 4) Технические риски и узкие места
1. **Жёстко зашит tenant/user path (`data/users/1`)**  
   Сейчас пути в нескольких местах захардкожены на пользователя `1`, что усложняет multi-tenant и переносимость окружений.

2. **Смешение источников состояния (JSON + SQL + отдельный SQLite dedupe)**  
   Данные размазаны по `accounts/groups/assignments` (JSON), основной БД (SQLAlchemy), и отдельному `data/dedupe.sqlite`. Это повышает сложность консистентности и восстановления после ошибок.

3. **Потенциальная гонка при дедупе**  
   В `ParserWorker` сначала выполняется SELECT на `ProcessedMessage`, затем INSERT. При параллельной обработке разными аккаунтами возможен конфликт уникальности на commit. Сейчас это не критично (rollback + retry loop продолжит), но стоит явно обрабатывать `IntegrityError` как ожидаемый сценарий.

4. **Запуск callback-loop в thread на import-time точки входа**  
   В `src/app.py` поток стартует при импорте модуля. Это может мешать тестированию и повторному использованию кода (side effects при import).

5. **Недостаток автоматических тестов**  
   В репозитории не обнаружен набор unit/integration тестов, что повышает риск регрессий при изменениях фильтрации/дедупа/форматирования.

## 5) Рекомендации (приоритет)
### P0 (высокий приоритет)
- Вынести все `data/users/1/...` в конфиг (например `settings.user_root`), чтобы убрать magic-path и облегчить масштабирование.
- Добавить явную обработку `IntegrityError` в месте записи `ProcessedMessage`/`UserChatHit` как нормального конкурентного кейса.
- Изолировать побочные эффекты старта бота: запуск thread переносить в функцию `main()`/CLI-команду, а не на уровне импорта.

### P1
- Свести хранение в единый источник: либо SQL-first (рекомендуется), либо чётко документировать границы JSON vs SQL.
- Добавить минимальные тесты:
  - `build_lead_message` (формат/кнопки),
  - matching по группам/keywords,
  - дедуп/TTL логика,
  - round-robin assignments.

### P2
- Добавить structured logging-контекст (account_id/chat_id/message_id) для лучшей диагностики.
- Улучшить README: архитектурная схема, setup, типичные команды, troubleshooting.

## 6) Быстрый итог
Репозиторий уже имеет рабочий каркас production-утилиты для Telegram lead parsing с понятной модульной структурой. Главные точки роста — управление конфигурацией путей, консистентность хранилищ и тестовое покрытие.
